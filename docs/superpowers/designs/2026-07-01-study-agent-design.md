## Problem Statement

当前知识通（Math Learning System）的右下角已有一个 `AIFab` 组件，但它只是“假 AI”：点击后弹出 3 个固定提示模板，返回预置的 mock 文本，没有真正的对话能力，也无法根据当前知识点上下文做个性化回答。学生在使用学习页面时，遇到不懂的概念只能离开系统去外部搜索或打开通用 AI 工具，学习流被打断。

本次要把它升级为真正的 `StudyAgent` 入口：
- 从右下角 FAB 展开为右侧 AI 对话 Sidebar（Drawer 宽度默认 380px，后续可扩展为 520px 两档；v1 只做 380px 固定宽度）；
- 对话能感知当前知识点（标题、层级、内容、学生的学习记录）；
- 每次回答后自动给出可点击的追问建议，降低学生“不知道该问什么”的门槛；
- 后台接入 KimiCode2.6 API，实现真正的多轮对话；
- 用 `Identity.md`、`Memory.md`、`SOULE.md` 配置 Agent 角色，并支持 Skill 与 Session 管理，为后续主动式学习规划 Agent 打基础。

## What Makes This Cool

1. **上下文感知的“家教”体验**：不是通用 AI，而是知道你在学“三角函数的基本概念”的数学辅导助手。学生问“sin 和 cos 怎么区分？”时，Agent 已经知道这个知识点的定义、常见错误、相关例题。
2. **零摩擦追问**：每次回答后自动弹出 3-4 个追问 chips（“能画个图吗？”“给我一道例题”“易错点是什么？”）。即使学生不知道下一步该问什么，也能被引导继续深入。
3. **可扩展的 Agent 架构**：用 Markdown 配置文件定义 Identity、Memory、Soul，Skill 可注册、Session 可持久化。第一版做对话，第二版就能做学习规划和薄弱点诊断。
4. **一次黑客松能讲完整的故事**：从右下小按钮 → 展开对话 → 真实 AI 回答 → 追问 → Session 历史。Demo 路径短，但每一步都看得见“智能”。

## Constraints

- **时间**：按黑客松/演示原型节奏，3-5 天内必须可运行、可展示。
- **技术栈**：前端 React 19 + Ant Design 6 + Vite；后端 NestJS + Prisma + PostgreSQL；已有 JWT 鉴权。
- **数据范围**：第一版只复用现有 `User`、`KnowledgePoint`、`LearningRecord` 的读取数据；需要新增两张极简表 `StudySession` 和 `StudyMessage` 来持久化对话，不引入新的业务实体（如错题本、个性化知识图谱）。
- **API 依赖**：需要真实可用的 KimiCode2.6 API key；后端通过环境变量 `KIMI_API_KEY` 接入。如果 demo 时 API 不可用，后端返回预置的友好降级回复，但保留真实架构和接口契约。
- **UI 兼容**：学习页面已有左侧知识树、中间内容、底部反馈面板，AI 面板以右侧 Drawer 形式展开，不破坏现有布局。全屏模式作为第二版体验增强，第一版可延后。

## Premises

1. 应该从现有右下角的 `AIFab` 扩展，而不是新建独立页面；入口保留在右下角，点击后展开为 Sidebar / 全屏对话。
2. 对学生用户最有价值的“哇点”是：AI 能感知当前知识点，进行多轮对话，并在每次回答后自动给出可点击的追问。
3. 黑客松 demo 需要接真实的 KimiCode2.6 API，而不是继续用 mock 响应；后端需要新增 `StudyAgent` 模块。
4. `SOULE.md` / `Identity.md` / `Memory.md`、Skill 管理、Session 管理这些是 demo 要展示的核心架构，即使第一版可以简化配置，但概念要到位。
5. 当前系统已有的知识点（`KnowledgePoint`）、学习记录（`LearningRecord`）、用户（`User`）数据足够让 Agent 做出有意义的上下文回答；第一版只需要新增 `StudySession`/`StudyMessage` 两张表来保存对话，不需要大量新数据模型。
6. 第一版只实现一个默认 Q&A Skill 和一份硬编码的 Agent 配置（`Identity.md` / `Memory.md` / `SOULE.md`）；Skill Registry 和动态配置加载作为可扩展接口保留，但不必在 demo 期完全实现。

## Approaches Considered

### Approach A: 最小可行方案
- **概要**：复用现有 `AIFab` 弹窗，仅把 mock 响应替换为真实 API 调用；后台一个 `/study-agent/chat` 端点，无 Session 表，历史上下文通过前端临时数组或 prompt 维护。
- **工作量**：S（1-2 天）
- **风险**：低
- **优点**：改动最小、最快可演示、不碰数据库 schema。
- **缺点**：无多轮历史、无追问建议、学生看不到“智能”的完整形态。
- **复用**：`AIFab.tsx`、`knowledgeApi`、NestJS 模块结构。

### Approach B: 演示级完整方案（推荐）
- **概要**：把 `AIFab` 扩展为可左滑/全屏的 Sidebar 对话面板；支持多轮对话、追问 chips、Session 持久化；后台新增 `StudyAgent` 模块 + KimiCode2.6 API；`Identity.md` / `Memory.md` / `SOULE.md` + Skill 注册。
- **工作量**：M（3-5 天）
- **风险**：中
- **优点**：与学生用户期望一致、demo 效果好、奠定后续主动式 Agent 的基础。
- **缺点**：需要数据库迁移、文件数增加、需要真实 API key。
- **复用**：`AIFab`、Ant Design `Drawer`、AuthContext、Prisma、react-query。

### Approach C: 全局入口方案
- **概要**：不把 AI 入口固定在 `LearningPage`，而是在导航增加全局“学习助手”页面，聚合多知识点对话、学习规划、错题回顾。
- **工作量**：L（5-7 天）
- **风险**：高
- **优点**：后期扩展性最强、能承载主动式学习规划 Agent 的愿景。
- **缺点**：破坏当前“围绕当前知识点”的上下文感知、短期内 demo 不够聚焦、改动范围最大。
- **复用**：较少，需要重新设计导航和上下文传递。

## Recommended Approach

**选择 Approach B。**

理由：
- 你前面已经明确想从现有 AIFab 扩展，并且 demo 的受众是“学生用户”。
- Approach B 在黑客松周期内可控（3-5 天），同时能完整展示“上下文感知 + 多轮对话 + 自动追问 + Agent 架构”。
- 它既不是只做 API 替换的“最小可行”（demo 太平淡），也不是重新做全局导航的“平台优先”（时间不够）。

## Data Model Additions

新增两张表，与现有 `User`、`KnowledgePoint` 关联：

```prisma
model StudySession {
  id                String   @id @default(uuid())
  userId            String
  knowledgePointId  String
  title             String   // 知识点标题，用于 UI 展示
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt
  user              User     @relation(fields: [userId], references: [id])
  knowledgePoint    KnowledgePoint @relation(fields: [knowledgePointId], references: [id])
  messages          StudyMessage[]

  @@unique([userId, knowledgePointId])
}

model StudyMessage {
  id        String   @id @default(uuid())
  sessionId String
  role      String   // 'user' | 'agent'
  content   String   // 文本内容
  followUps Json?    // 追问 chips 数组，如 ["追问1", "追问2", "追问3"]
  createdAt DateTime @default(now())
  session   StudySession @relation(fields: [sessionId], references: [id], onDelete: Cascade)
}
```

第一版不做软删除、不保留已删除消息历史。

## Knowledge Content Reading

`KnowledgePoint` 表本身不存储完整 Markdown 内容，内容文件保存在 `iksm/{textbookName}.md`。`StudyAgentService` 需要复用或扩展 `TextbookService` 读取文件内容：

- 通过 `knowledgePoint.textbookId` 找到对应 textbook；
- 读取 `textbook.contentPath` 指向的 Markdown 文件；
- 按知识点 `code` 或标题定位对应章节：
  - 优先匹配 `# {code} {title}`、`## {code} {title}` 等标题；
  - 其次匹配标题中出现知识点 `title` 的段落；
  - 若都失败，fallback 为整个 Markdown 文件前 2000 字符；
- 截取该章节内容前约 2000 字符（按 token 更优，v1 先用字符做近似），注入 prompt。截断时尽量在段落或公式块边界处切断，避免截断 LaTeX 公式或 Mermaid 代码块；若无法避免，则丢弃不完整的公式块。

v1 不实现全文检索，只注入当前知识点内容。如果文件不存在或章节定位失败，prompt 中只使用知识点标题和层级路径。

## Open Questions → Decisions

1. **KimiCode2.6 API 接入方式**：后端 NestJS 代理调用，不暴露 key 到前端。`KimiCode2.6` 是项目内部约定的模型/服务名称；对外实现时映射到 Moonshot Kimi 的 OpenAI-compatible REST endpoint（`https://api.moonshot.cn/v1/chat/completions`）或内部网关地址。最终部署前需确认 `KIMI_BASE_URL` 和 `KIMI_MODEL`。第一版不走 SSE，使用同步 JSON 请求（timeout 30s）；流式响应放到第二版优化。
2. **追问 chips 的生成策略**：由 LLM 在回答末尾按固定 JSON 格式输出 3 个追问，后端解析后返回；解析失败时由后端根据知识点规则兜底生成 3 个通用追问（如“能举个例子吗？”“易错点是什么？”“给我一道练习题”）。
3. **Session 的粒度**：一个知识点一个 Session。切换知识点时，若当前知识点已有历史 Session 则恢复，否则创建新 Session。用户登出/刷新页面后，通过 `userId + knowledgePointId` 重新查询历史 Session。
4. **Agent 配置文件的加载方式**：三个 Markdown 文件统一放在 `server/study-agent-config/` 目录下，启动时读取并缓存在内存；第一版只读默认配置，不支持热加载或教师后台编辑。
5. **Skill 注册的第一版范围**：只实现一个默认 Skill `qa`，内部调用 Kimi API。Skill Registry 设计为接口，但第一版只注册 `qa` 一个实现，后续可扩展为 `quiz`、`explain`、`plan` 等。
6. **失败/降级策略**：当 API 超时、限流或返回错误时，后端返回预置的友好回复（“AI 助手暂时不可用，请稍后重试”），并记录日志；不自动切回 mock 内容，避免学生看到与问题无关的预置文本。

## KimiClient & SDK

- **依赖**：使用 `openai` 官方 SDK 或直接用 `axios` 调用 Moonshot 兼容 OpenAI 的 endpoint。若使用 SDK，在 `server/package.json` 中安装 `openai`；若用 `axios`，需自行封装请求和错误处理。
- **配置项**：`KIMI_BASE_URL`（可选，默认 `https://api.moonshot.cn/v1`）、`KIMI_API_KEY`、`KIMI_MODEL`（如 `kimi-k1-5` 或项目内部代号 `kimi-code-2.6`）。
- **调用参数**：temperature 0.7，max_tokens 1024，top_p 0.9。
- **错误处理**：封装 4 类错误：鉴权失败、超时（>30s）、限流/服务不可用、内容过滤；统一映射为 503 或 500 并记录。
- **模型名称**：`KimiCode2.6` 是产品/内部代号，实际部署时通过 `KIMI_MODEL` 环境变量映射到真实模型名称。

## Agent Configuration

第一版使用三个 Markdown 文件定义默认 Agent 角色，统一放在 `server/study-agent-config/`：

- **Identity.md**：角色身份、语气、教学风格。示例内容：
  ```markdown
  # Identity
  你是一名耐心、善于引导的高中数学助教。你的名字是“小知”。
  - 当学生问概念时，先用一句话给出核心定义，再用一个具体例子说明。
  - 当学生问题目时，不要直接给答案，而是给出解题步骤和关键提示，让学生自己推导。
  - 使用简体中文，数学公式用 LaTeX。
  ```
- **Memory.md**：长期记忆与全局约束。示例内容：
  ```markdown
  # Memory
  - 学生是高中生，使用教材大纲学习。
  - 回答应简洁，控制在 300 字以内，除非学生要求展开。
  - 优先使用学生当前正在学习的知识点作为上下文。
  ```
- **SOULE.md**：灵魂/价值观层（SOULE = Soul, Objective, Understanding, Learning, Evaluation 的缩写，也可简化为 SOUL）。示例内容：
  ```markdown
  # SOULE
  - 目标是帮助学生真正理解，而不是快速完成题目。
  - 鼓励学生提问、犯错、再修正。
  - 每次回答后，提供 3 个与当前知识点相关的追问，引导学生深入思考。
  ```

启动时由 `StudyAgentConfigService` 读取三文件并拼接成 system prompt。第一版不支持热加载或按教师/科目切换配置。

## API Contract

后端新增 `StudyAgentController`，前缀 `/api/study-agent`，受 `JwtAuthGuard` 保护。

### 1. 创建会话
```http
POST /api/study-agent/sessions
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "knowledgePointId": "xxx"
}
```

若该用户+知识点已存在 Session，则返回现有 Session；否则创建新 Session。实现使用 Prisma `upsert` 避免并发竞争。响应包含 `id` 和空 `messages` 列表。

### 2. 发送消息
```http
POST /api/study-agent/sessions/:sessionId/messages
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "content": "sin 和 cos 怎么区分？"
}
```

响应：
```json
{
  "success": true,
  "data": {
    "userMessage": { "id": "...", "role": "user", "content": "sin 和 cos 怎么区分？" },
    "agentMessage": {
      "id": "...",
      "role": "agent",
      "content": "可以用单位圆来记忆...",
      "followUps": ["能画个图说明吗？", "给我一道例题", "易错点是什么？"]
    }
  }
}
```

### 3. 获取会话
```http
GET /api/study-agent/sessions/:sessionId
Authorization: Bearer <jwt>
```

响应包含 `messages` 列表（按 `createdAt` 升序）。

### 4. 错误码
- `400`：请求参数缺失或 `knowledgePointId` 无效。
- `401`：未鉴权。
- `404`：指定的 Session 不存在或无权访问。
- `429`：用户触发限流，提示稍后再试。
- `503`：Kimi API 不可用或超时，返回友好降级消息。

> v2 预留：`GET /api/study-agent/sessions` 查询用户的所有会话，用于“学习助手主页”。v1 不实现。

## Skill Registry（第一版最简实现）

第一版不做过度的动态注册抽象，只用一个 Map 把 `qa` 名字映射到唯一实现：

```typescript
interface StudySkill {
  name: string
  description: string
  execute(params: { messages: StudyMessage[]; context: KnowledgeContext }): Promise<AgentResponse>
}

class StudySkillRegistry {
  private readonly skills = new Map<string, StudySkill>()

  register(skill: StudySkill): void {
    this.skills.set(skill.name, skill)
  }

  async execute(name: string, params: { messages: StudyMessage[]; context: KnowledgeContext }): Promise<AgentResponse> {
    const skill = this.skills.get(name)
    if (!skill) throw new Error(`Skill ${name} not found`)
    return skill.execute(params)
  }
}
```

启动时 `StudyAgentModule` 只注册一个 `qaSkill`：
- 接收历史 messages + 当前知识点上下文；
- 按固定 prompt 模板调用 Kimi API；
- 解析回答正文与追问 JSON；
- 返回 `content` + `followUps`。

这样 Skill Registry 的接口留出来了，但第一版只有一条硬编码路径，没有额外复杂度。

## LLM Output Format

要求模型按以下规则输出：

1. **正文**：使用 Markdown + LaTeX 回答学生问题。
2. **追问**：在回答末尾，必须追加一个独立的 JSON 代码块，格式如下：
   ```json
   {
     "followUps": ["追问1", "追问2", "追问3"]
   }
   ```
   - `followUps` 固定为 3 个追问（v1 不做 1-4 动态数量）。
   - 追问必须与当前知识点和学生上一问题相关。
   - JSON 代码块前后用空行分隔，便于正则解析。

System prompt 中明确说明上述规则，并在末尾给出一次示例。

**解析策略（降低模型不遵循格式的风险）**：
- 使用正则提取最后的 Markdown JSON 代码块；
- 若提取失败，尝试匹配最后一个独立的 `{"followUps": [...]}` JSON 对象；
- 若仍失败，使用规则兜底生成 3 个通用追问（见“追问兜底”）。

**追问兜底**：
- 若知识点有定义：`["能举个例子吗？", "易错点是什么？", "给我一道练习题"]`；
- 否则：`["再详细说明一下", "这个概念和之前学的有什么联系？", "还有什么需要注意的？"]`。

第一版不使用 function calling 或 JSON mode，因为需要同时返回 Markdown 正文和结构化追问。v2 可评估更严格的结构化输出方案。

## Prompt Template

默认 `qaSkill` 发送给 LLM 的消息结构：

```typescript
[
  { role: 'system', content: systemPrompt }, // Identity + Memory + SOULE 拼接
  { role: 'system', content: knowledgeContext }, // 知识点标题 + 层级 + 内容摘要
  { role: 'system', content: learningContext }, // 最近 3 条学习记录摘要
  ...historyMessages, // 最近 6 条对话
  { role: 'user', content: currentUserMessage },
]
```

`systemPrompt` 示例（由 Identity/Memory/SOULE 拼接）：

```markdown
你是一名耐心、善于引导的高中数学助教。你的名字是“小知”。
- 当学生问概念时，先用一句话给出核心定义，再用一个具体例子说明。
- 当学生问题目时，不要直接给答案，而是给出解题步骤和关键提示，让学生自己推导。
- 使用简体中文，数学公式用 LaTeX。
- 回答应简洁，控制在 300 字以内，除非学生要求展开。
- 你的目标是帮助学生真正理解，而不是快速完成题目。
- 每次回答后，必须提供 3 个与当前知识点相关的追问，引导学生深入思考。
- 在回答末尾，追加一个独立的 JSON 代码块，格式如下：
  ```json
  {
    "followUps": ["追问1", "追问2", "追问3"]
  }
  ```
```

`knowledgeContext` 示例：

```markdown
当前知识点：三角函数的基本概念（高中数学 > 三角函数）
内容摘要：
在平面直角坐标系中，设角 α 的顶点与原点重合，始边与 x 轴非负半轴重合，终边上任一点 P(x,y)，记 r = |OP| = √(x² + y²)。
sin α = y/r, cos α = x/r, tan α = y/x
```

## Context & Prompt Strategy

每次调用 LLM 时，prompt 按以下顺序组装成一条 system message 和若干 user/assistant message（若 SDK/模型不支持多条 system message，则先拼接成一条）：

1. **System prompt**：`Identity.md` + `Memory.md` + `SOULE.md` 拼接为一段；
2. **Knowledge context**：当前知识点标题 + 层级路径 + Markdown 内容摘要（约 2000 字符）；
3. **Learning context**：学生该知识点的最近 3 条学习记录（按 `startTime` DESC 取最近 3 条，含 `masteryLevel`、`durationMinutes`），用于调整回答深度；
4. **Conversation history**：当前 Session 中最近 6 条消息（按 `createdAt` DESC 取最近 6 条，再按时间升序排列，用户 + Agent 交替）；
5. **Current user message**。

**Token budget**：v1 目标总 prompt 控制在约 3000-4000 tokens 以内。若超过，优先截断知识点内容摘要，其次截断 history 条数（但最少保留 2 条），最后简化 learning context。系统 prompt 和当前用户问题不截断。

第一版不联网、不检索外部资料，只基于系统 prompt 和本地上下文回答。

## Edge Cases & Security

- **欢迎语**：新 Session 的第一条 Agent 消息固定为欢迎语，不调用 LLM。例如“你好！我是你的学习助手小知。你现在正在学习《三角函数的基本概念》，有问题随时问我。”
- **发送中状态**：用户点击发送后，输入框清空、发送按钮变为禁用并显示 loading；等待后端返回期间，消息列表底部显示“AI 正在思考…”占位。
- **API 错误展示**：前端收到 503 时显示“AI 助手暂时不可用，请稍后重试”；收到 429 时显示“请求太频繁，请稍后再试”；收到 401 时重定向到登录页。
- **超长对话**：数据库保留全部消息，但 prompt 中只使用最近 6 条消息；超过 Token 预算时继续截断知识点内容，按段落/公式块边界截断，优先保留标题和完整公式块。
- **空知识点**：若用户在学习页外点击 FAB（无 `knowledgePointId`），显示通用欢迎语，不调用 LLM，提示“请先选择一个知识点”。
- **上下文切换**：切换知识点后，前端调用 `POST /api/study-agent/sessions`（带 `knowledgePointId`）获取或创建 Session，再 `GET /api/study-agent/sessions/:id` 拉取历史；不跨知识点混合会话。
- **Rate limiting & cost**：v1 在后端做简单内存限流（适合单实例部署）——每个用户每分钟最多 20 次调用、每小时最多 100 次；超出返回 429 并提示稍后再试。多实例部署时改用 Redis 或数据库计数。按每次调用约 2000 input tokens / 500 output tokens 估算，单次成本约 0.003-0.008 RMB（以 Kimi 公开定价为参考）。
- **数据隐私**：用户问题和学习记录仅通过后端发送到 Kimi API，不记录原始 prompt 到本地日志（只记录 message 摘要和 API 错误）。不在 prompt 中注入用户 PII（如姓名、邮箱）。
- **内容安全**：Agent 回复不直接展示数学公式以外的大型 HTML；Markdown 使用现有 `MarkdownPreview` 组件渲染，已支持 KaTeX 和 Mermaid。
- **鉴权**：所有 study-agent 端点受 `JwtAuthGuard` 保护；Session 查询必须匹配 `userId`，防止用户 A 读取用户 B 的对话。

## Error Handling & Fallback

- **开发阶段**：如果无 `KIMI_API_KEY`，后端 `KimiClient` 抛明确错误，`StudyAgentService` 返回 503 降级消息（“AI 助手暂时不可用，请稍后重试”）。不保留“假装 AI 回答”的预置 mock 内容，避免与真实架构混淆。
- **集成测试**：可录制 Kimi API 的真实响应样本，用于无 key 时的离线测试，但生产代码不返回录制内容。

## Testing Strategy

- **后端单元测试**：
  - mock `KimiClient` 和 `StudyAgentConfigService`，测试 prompt 组装、追问解析、Session 创建、鉴权失败；
  - 测试追问解析器的鲁棒性：正常 JSON 块、缺失 JSON 块、JSON 格式错误、多余 Markdown 等；
  - 测试 `POST /api/study-agent/sessions` 的 upsert 行为和并发安全性。
- **前端单元测试**：
  - mock `studyAgentApi` 和 `AuthContext`，测试 `StudyAgentPanel` 渲染、消息列表、追问点击、输入发送、错误状态展示。
- **E2E 验证**：
  - 用真实 API key 跑一条完整对话，确认追问 JSON 被正确解析、Session 被持久化。
- **解析器测试**：收集 10-20 条真实模型输出，验证解析器成功率，低于 80% 则改为更严格的 prompt 或 JSON mode。

## Success Criteria

- [ ] 切换知识点时，能恢复该知识点下的历史对话（按 `userId + knowledgePointId` 查询）。

- [ ] `server/study-agent-config/` 下存在 `Identity.md`、`Memory.md`、`SOULE.md`，并在 system prompt 中生效。
- [ ] API 超时/不可用时返回 503 降级消息，不暴露内部错误详情。
- [ ] `pnpm typecheck` 和 `pnpm lint` 通过；核心 service 和组件有单元测试。

本版本不做：
- 流式响应（SSE）
- 全屏模式（v2 再考虑，v1 只做右侧固定宽度 Drawer）
- 动态 Skill 配置/教师后台编辑
- 主动式学习规划（如自动推送复习计划）
- 多模态输入（图片、手写公式）
- 外部检索/联网搜索
- `GET /api/study-agent/sessions` 全量会话列表（v2 学习助手主页使用）
